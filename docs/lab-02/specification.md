# TokTickIT Requester Ticketing MVP — Lab 2 Specification

## 1. Sprint Goal

Deliver a responsive Requester-facing ticketing MVP that allows a selected Development Requester to create an IT support Ticket, receive an official backend-generated Ticket Number, view only their own Tickets, search/filter/sort/paginate those Tickets, open Ticket Detail, and manage permitted Attachments.

## 2. Stakeholder Request

TokTickIT needs a simple and professional Requester experience for submitting IT support requests. A Requester must be able to provide the problem information, select the affected category and system, choose a requested priority, optionally provide permitted Attachments, and later find and inspect their own Tickets.

Lab 2 uses a temporary Development Requester selector instead of real authentication. This selector represents the currently selected Requester for testing only. Real authentication and role-based access are outside the scope of this Lab and will be introduced in Lab 3.

## 4. Functional Requirements

### Ticket and Requester

**FR-01** The system shall provide a Development Requester Selection screen before requester-specific Ticket screens can be used.

**FR-02** The system shall load only active Development Requesters from PostgreSQL.

**FR-03** The system shall display the currently selected Requester in the application shell.

**FR-04** The system shall allow the user to change the selected Development Requester.

**FR-05** Changing the selected Requester shall reload requester-specific Ticket data.

### Create Ticket

**FR-06** The Create Ticket screen shall provide Ticket Number, Ticket Date, Requester, Category, Related System, Ticket Summary, Requested Priority, Description, and Attachments.

**FR-07** Ticket Number shall be generated by the backend after successful Ticket creation and shall be read-only in the UI.

**FR-08** Ticket Date shall be generated by the backend and shall be read-only in the UI.

**FR-09** Current Status shall be initialized by the backend as `New`.

**FR-10** The Requester field shall use the currently selected Development Requester and shall not be manually editable on the Create Ticket form.

**FR-11** The system shall validate required fields on both frontend and backend.

**FR-12** The system shall trim leading and trailing whitespace from text inputs before validation and persistence.

**FR-13** The system shall prevent duplicate submission while a Ticket creation request is being processed.

**FR-14** A successful Ticket creation shall return the official Ticket Number and saved Ticket information.

### My Tickets

**FR-15** The system shall display only Tickets owned by the selected Development Requester.

**FR-16** My Tickets shall support text search.

**FR-17** My Tickets shall support filtering by documented Ticket fields.

**FR-18** My Tickets shall support sorting by documented Ticket fields.

**FR-19** My Tickets shall support pagination.

**FR-20** My Tickets shall provide loading, empty, no-results, and API-failure states.

### Ticket Detail

**FR-21** The system shall retrieve one Ticket Detail only when the Ticket belongs to the selected Development Requester.

**FR-22** Ticket Detail shall display current Ticket information as read-only.

**FR-23** Ticket Detail shall provide the permitted Attachment lifecycle functions.

### Attachments

**FR-24** The system shall allow JPG/JPEG, PNG, WEBP, and PDF Attachments.

**FR-25** The maximum Attachment size shall be 5 MB per file.

**FR-26** A Ticket shall have no more than five active Attachments.

**FR-27** Attachment removal shall be soft removal.

**FR-28** Removed Attachments shall remain represented by metadata but shall not be downloadable or previewable.

**FR-29** Attachment operations shall enforce Ticket ownership through the selected Development Requester.

### Reference Data

**FR-30** The system shall retrieve active Categories.

**FR-31** The system shall retrieve active Related Systems.

**FR-32** The system shall retrieve active Development Requesters.

## 5. Business Rules

**BR-01 — Ticket Number**
The official Ticket Number is generated by the backend and must be unique.

**BR-02 — Ticket Status**
Every newly created Ticket starts with Current Status `New`.

**BR-03 — Ticket Date**
Ticket Date is generated by the backend at successful Ticket creation and is not supplied by the Requester.

**BR-04 — Development Requester**
The selected Development Requester represents the current Requester for Lab 2 testing only and is not authentication.

**BR-05 — Active Requesters**
Only active Development Requesters are available in the Requester selector.

**BR-06 — Requester Required**
A Development Requester must be selected before Create Ticket, My Tickets, or Ticket Detail requester-specific operations can be used.

**BR-07 — Requester Switching**
Changing the selected Requester immediately changes the requester context and reloads requester-specific data.

**BR-08 — Requester Ownership**
A Requester may view only Tickets belonging to the currently selected Development Requester.

**BR-09 — Detail Ownership**
A Ticket Detail request for a Ticket owned by another Requester shall not return the Ticket data.

**BR-10 — Attachment Ownership**
Attachment metadata, download, upload, and soft removal require the parent Ticket to belong to the selected Requester.

**BR-11 — Summary Required**
Ticket Summary is required and must contain 5–200 characters after trimming.

**BR-12 — Description Required**
Description is required and must contain 10–5000 characters after trimming.

**BR-13 — Category Required**
A valid active Category is required.

**BR-14 — Related System Required**
A valid active Related System is required.

**BR-15 — Requested Priority Required**
Requested Priority is required and must be one of `LOW`, `MEDIUM`, `HIGH`, or `URGENT`.

**BR-16 — Requester Validation**
A Ticket creation request must reference a valid active Development Requester.

**BR-17 — Reference Data Validation**
Inactive or nonexistent Category and Related System values cannot be used to create a Ticket.

**BR-18 — Duplicate Submission Prevention**
The Create Ticket action is disabled while the creation request is in progress. A repeated client submission must not create multiple Tickets from one user action.

**BR-19 — Validation Location**
Validation shall occur both in the frontend for immediate feedback and in the backend as the authoritative validation layer.

**BR-20 — Failure Data Retention**
When a Ticket creation request fails because of validation or an API/server error, the user's entered form values shall remain available so the user can correct or retry without re-entering the data.

**BR-21 — Ticket List Search**
Search matches Ticket Number and Ticket Summary.

**BR-22 — Ticket List Filters**
The list supports filtering by Category, Requested Priority, and Current Status.

**BR-23 — Ticket List Sorting**
The list supports sorting by Ticket Date, Ticket Number, and Last Updated.

**BR-24 — Default Sorting**
The default Ticket list ordering is Last Updated descending, with Ticket Number descending as the secondary sort.

**BR-25 — Pagination**
Page numbering starts at 1. Supported page sizes are 10, 20, and 50.

**BR-26 — Invalid Pagination**
Invalid page or page-size values are rejected with a safe validation response rather than silently producing unpredictable results.

**BR-27 — No Search Results**
A valid search/filter operation that matches no Tickets displays a dedicated no-results state and does not display unrelated Tickets.

**BR-28 — Empty Ticket List**
A Requester with no Tickets displays a dedicated empty state with an action to Create Ticket.

**BR-29 — Attachment Types**
Only JPG/JPEG, PNG, WEBP, and PDF files are accepted.

**BR-30 — Attachment Size**
Each Attachment must be no larger than 5 MB.

**BR-31 — Attachment Count**
A Ticket may have at most five active Attachments.

**BR-32 — Attachment Metadata**
Each Attachment stores at least original filename, safe stored filename or storage key, MIME type, file size, upload timestamp, and removal state.

**BR-33 — Safe Filename**
Original filenames are treated as display metadata only. Stored filenames/storage keys must be generated safely by the server and must not rely directly on untrusted path input.

**BR-34 — Attachment Upload Failure**
If Ticket creation succeeds but one or more Attachment uploads fail, the Ticket remains saved and the UI reports the failed Attachment operation without deleting the successfully created Ticket.

**BR-35 — Attachment Removal Reason**
Soft removal requires an explicit confirmation and a non-empty removal reason.

**BR-36 — Soft Removal**
Removing an Attachment sets its removal state instead of deleting its metadata record.

**BR-37 — Removed Attachment Access**
A removed Attachment must not be downloadable or previewable.

**BR-38 — Attachment Display**
Removed Attachments remain identifiable as removed metadata but their download/preview actions are unavailable.

**BR-39 — Unexpected Errors**
Unexpected server errors return safe messages and must not expose stack traces, SQL details, filesystem paths, or internal implementation information.

**BR-40 — Lab 3 Transition**
The selected Development Requester identifier shall remain associated with Tickets so the Lab 3 authentication implementation can later replace the testing selector without redesigning Ticket ownership relationships.

## 7. Data Changes

The PostgreSQL design shall support:

- Development Requester
- Ticket
- Attachment
- Category
- Related System

### Core relationships

- One Requester → many Tickets.
- One Ticket → one Requester.
- One Ticket → many Attachments.
- One Category → many Tickets.
- One Related System → many Tickets.

### Ticket fields

- `id`: primary key.
- `ticketNumber`: unique official Ticket Number.
- `ticketDate`: backend-generated timestamp.
- `requesterId`: foreign key to Development Requester.
- `categoryId`: foreign key to Category.
- `relatedSystemId`: foreign key to Related System.
- `summary`: required text.
- `description`: required text.
- `requestedPriority`: enum.
- `currentStatus`: enum, initially `New`.
- `createdAt`: timestamp.
- `updatedAt`: timestamp.

### Attachment fields

- `id`: primary key.
- `ticketId`: foreign key to Ticket.
- `originalFilename`: display metadata.
- `storageKey`: server-generated storage identifier.
- `mimeType`.
- `fileSize`.
- `uploadedAt`.
- `removedAt`: nullable timestamp.
- `removalReason`: nullable text.

Soft removal is represented by `removedAt != null`.

Indexes should support:

- unique Ticket Number;
- Ticket requester ownership lookup;
- Ticket date/updated-at sorting;
- category filtering;
- priority filtering;
- status filtering;
- Attachment Ticket lookup and removal filtering.

## 9. Acceptance Criteria

### AC-01 — Requester selection

**Given** active Development Requesters exist,
**When** the user opens the application,
**Then** the Requester Selection screen displays the active Requesters and allows one to be selected.

### AC-02 — No requester selected

**Given** no Development Requester has been selected,
**When** the user attempts to access requester-specific Ticket screens,
**Then** the Requester Selection screen is shown.

### AC-03 — Inactive requester exclusion

**Given** an inactive Development Requester exists,
**When** the Requester selector loads,
**Then** the inactive Requester is not shown.

### AC-04 — Requester switching

**Given** Requester A is selected,
**When** the user changes to Requester B,
**Then** the application displays Requester B and reloads requester-specific data.

### AC-05 — Valid Ticket creation

**Given** valid Ticket data and a selected active Requester,
**When** the Requester submits the form,
**Then** exactly one Ticket is saved, the backend generates a unique Ticket Number, and the official Ticket Number is displayed.

### AC-06 — Default Ticket state

**Given** a Ticket is successfully created,
**When** the saved Ticket is retrieved,
**Then** its Current Status is `New` and its Ticket Date was generated by the backend.

### AC-07 — Required-field validation

**Given** one or more required fields are empty or invalid,
**When** the Requester submits the form,
**Then** field-level validation messages are displayed and the API is not called.

### AC-08 — Backend validation

**Given** an invalid Ticket creation request bypasses frontend validation,
**When** the request reaches the API,
**Then** the backend rejects it with a documented 4xx validation response and does not create a Ticket.

### AC-09 — Duplicate submission

**Given** a Ticket submission is in progress,
**When** the user attempts to submit again,
**Then** the Submit action remains disabled/busy and another Ticket is not created.

### AC-10 — Failure retention

**Given** Ticket creation fails because of an API/server error,
**When** the error is shown,
**Then** the user's entered form values remain available for correction or retry.

### AC-11 — Ownership list

**Given** Requester B is selected,
**When** My Tickets loads,
**Then** only Requester B's Tickets are returned and displayed.

### AC-12 — Cross-requester detail protection

**Given** Requester B is selected,
**When** a Ticket belonging to Requester A is requested,
**Then** the Ticket data is not returned.

### AC-13 — Search

**Given** a Requester has multiple Tickets,
**When** a search term matching a Ticket Number or Summary is entered,
**Then** only matching owned Tickets are displayed.

### AC-14 — Filters

**Given** the Requester has Tickets with different Categories, Requested Priorities, or Statuses,
**When** a filter is applied,
**Then** only owned Tickets matching the selected filter are returned.

### AC-15 — Sorting

**Given** the Requester has multiple Tickets,
**When** a supported sort is selected,
**Then** the Tickets are returned in the requested order with the documented secondary sort.

### AC-16 — Pagination

**Given** the Requester has more Tickets than the selected page size,
**When** the Requester changes pages,
**Then** the API returns only the requested page and accurate pagination metadata.

### AC-17 — Empty and no-results states

**Given** a Requester has no Tickets or a valid search/filter has no matches,
**When** My Tickets loads,
**Then** the appropriate empty or no-results state is displayed.

### AC-18 — Create Ticket Attachment rules

**Given** the Requester selects an Attachment,
**When** the file is checked,
**Then** only JPG/JPEG/PNG/WEBP/PDF files up to 5 MB are accepted and no Ticket can have more than five active Attachments.

### AC-19 — Attachment upload

**Given** an owned Ticket exists,
**When** the Requester uploads a permitted Attachment within the active Attachment limit,
**Then** the Attachment metadata is saved and displayed.

### AC-20 — Attachment removal

**Given** an Attachment belongs to an owned Ticket,
**When** the Requester confirms removal with a reason,
**Then** the Attachment becomes soft-removed and its metadata remains available.

### AC-21 — Removed Attachment protection

**Given** an Attachment has been soft-removed,
**When** the Requester attempts to download or preview it,
**Then** the operation is rejected and no file content is returned.

### AC-22 — Attachment ownership

**Given** Requester B is selected,
**When** Requester B attempts to access an Attachment belonging to Requester A's Ticket,
**Then** the Attachment operation is rejected without exposing the resource.

### AC-23 — API failure states

**Given** an API operation fails unexpectedly,
**When** the UI receives the failure,
**Then** a safe user-facing error is displayed and sensitive implementation details are not exposed.

### AC-24 — Responsive behavior

**Given** the application is opened at desktop, tablet, or mobile viewport sizes,
**When** the requester uses Create Ticket, My Tickets, or Ticket Detail,
**Then** controls remain usable, content is not clipped or overlapped, and mobile screens do not require horizontal page scrolling.

### AC-25 — Accessibility

**Given** the user navigates the UI using keyboard controls,
**When** forms, buttons, selectors, and icon-only actions are used,
**Then** controls have visible focus indicators, accessible labels where required, and clear validation feedback.

## 11. Assumptions and Decisions

1. Ticket Number format will be generated by the backend using a human-readable prefix and date/sequence structure. The exact format is an implementation detail, but uniqueness is enforced by the database.
2. Ticket Date uses the backend timestamp rather than client time.
3. Requested Priority uses `LOW`, `MEDIUM`, `HIGH`, and `URGENT`.
4. Ticket Summary uses 5–200 characters after trimming.
5. Description uses 10–5000 characters after trimming.
6. Page numbering starts at 1 and supported page sizes are 10, 20, and 50.
7. Search applies to Ticket Number and Ticket Summary.
8. Ticket-list filters are Category, Requested Priority, and Current Status.
9. Ticket-list sorting supports Ticket Date, Ticket Number, and Last Updated.
10. Attachment upload is a separate API operation after Ticket creation, allowing the Ticket to remain saved when an Attachment upload fails.
11. Removed Attachment metadata remains visible so the system can demonstrate soft removal, but removed file content is inaccessible.
12. Lab 2 ownership is simulated through the selected Development Requester ID. This mechanism is intentionally designed so that Lab 3 authentication can later supply the real requester identity.
